# 5. LSP Subprocess Client Pooling for Semantic Cross-File Resolution

Date: 2026-08-14

## Status

Accepted

## Context

Tree-sitter AST heuristics cannot reliably determine exact jump-to-definition targets across complex module imports, third-party libraries, and overloaded symbol hierarchies. Language Server Protocol (LSP) servers (such as `pyright`, `rust-analyzer`, `gopls`, `tsserver`) provide 100% accurate semantic symbol resolution, but are designed for interactive single-user editors rather than high-throughput batch indexers.

## Decision

Integrate a headless Language Server Protocol manager (`LSPClientPool` / `LSPClient`):
1. Spawn subprocess instances of available language servers using JSON-RPC over `stdio`.
2. Manage concurrent requests using a thread-safe connection pool (`lsp_pool_size`).
3. Feed document updates (`textDocument/didOpen`) and batch-query `textDocument/definition` positions during index extraction.
4. Translate LSP definition coordinates into exact caller-to-callee `CALLS` edges stored in Gorgonzola.

## Consequences & Trade-offs

### Positive
- Precise, compiler-grade cross-file definition resolution for statically verifiable calls.
- Eliminates false-positive call edges generated by pure syntactic symbol heuristics.

### Brutal Realities & Flaws
- **Heavy Resource Footprint**: Spawning multiple language server processes (especially memory-intensive daemons like `pyright` or `rust-analyzer`) drastically increases memory usage and startup time.
- **Process Lifecycle Flakiness**: LSP subprocesses are prone to deadlocks, slow startup times, or lingering orphan processes if termination sequences (`shutdown` -> `exit` -> `kill`) are interrupted or fail.
- **Strict Timeout Constraints**: Batch indexing with LSP requires aggressive per-request timeouts (`lsp_request_timeout=5.0s`). If an LSP server lags or re-indexes internally, requests time out and fall back to Tree-sitter heuristics.
